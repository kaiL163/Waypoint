# Waypoint

React-диспетчерская + FastAPI, OR-Tools, OSRM и PostgreSQL/PostGIS. Интерфейс сохраняет прежние цвета, логотип, карту и структуру.

## Запуск целиком

Нужен Docker Desktop с Linux containers. В корне проекта:

```powershell
docker compose up -d --build
```

Сайт: http://localhost:5173

Swagger: http://localhost:5173/docs

Состояние сервисов: `docker compose ps`

Логи: `docker compose logs --tail 100 backend osrm-prepare`

Первый запуск скачивает карту Москвы (~81 МБ) и готовит отдельные графы car / foot / bicycle. Это занимает несколько минут и несколько ГБ диска; для Docker желательно выделить 6–8 ГБ RAM. Frontend стартует после подготовки графов и готовности API. Повторный запуск использует сохранённые графы.

Если порт занят, в PowerShell перед запуском: `$env:WAYPOINT_PORT='5180'`. Открывайте соответствующий порт. Не запускайте Vite и Docker frontend на одном порту.

Необязательные настройки перечислены в `.env.example`; создайте собственный `.env` в корне при необходимости. Не меняйте пароль уже созданной БД только через env: это не меняет пароль внутри PostgreSQL.

Остановка с сохранением данных: `docker compose stop`. Запуск: `docker compose up -d`. **Не используйте `down -v` для обычной остановки — это удаляет тома БД и графов.**

## Архитектура

- frontend: React / TypeScript / Leaflet, production-сборка через nginx; API проксируется тем же origin.
- backend: FastAPI, проверка входных данных, загрузка CSV/JSON, события, объяснения и сравнение.
- OR-Tools: VRPTW с разными матрицами переездов для каждого транспорта, навыками, окнами начала работ и сменами.
- OSRM: три независимых сервиса, графы из одного OSM-экстракта Москвы. Автомобиль учитывает автомобильные дороги; пешеход и велосипед — разрешённые пути соответствующего профиля. Это не гарантия наличия отдельного тротуара на каждом участке OSM.
- PostgreSQL: текущий набор, оба плана, версии и история снимков. PostGIS: точки инженеров и заявок EPSG:4326 с пространственным индексом. Версионная запись защищает от перезаписи результата из устаревшей вкладки (HTTP 409).

Таблицы `waypoint_*_v2` не перезаписывают старые таблицы предыдущих реализаций. Старые наборы автоматически не мигрируются. История хранится в БД, интерфейс её восстановления пока не реализован.

## Правила расчёта по ТЗ

1. Работа **начинается** между windowStart и windowEnd включительно. Завершение может быть позже конца окна, но не позже конца смены.
2. Инженер имеет нужный навык и, если указан, требуемый транспорт. Нет пересечения работ и переездов. Возврат на старт не требуется.
3. Базовый алгоритм идёт строго по входному порядку заявок и назначает первому допустимому инженеру во входном порядке.
4. Цели оптимизации по приоритету: меньше неназначенных срочных → меньше всех неназначенных → меньше задействованных инженеров → меньше пробега. Штрафы рассчитаны относительно верхней границы стоимости маршрутов. Результат дополнительно сравнивается с базовым по этой же последовательности.
5. Поиск ограничен MAX_SOLVE_SECONDS (по умолчанию до 10 секунд, меньше для малых наборов). Это эвристический поиск допустимого решения, не доказательство глобального оптимума.
6. Все события имеют время: срочная заявка, отмена, недоступность инженера. Перепланируется остаток дня, новая работа не начинается до события.
7. Допущение прототипа: инженер выезжает сразу после предыдущей работы или начала смены/перепланирования. Уже начатая поездка, ожидание на адресе и работа зафиксированы. При недоступности инженер завершает текущую зафиксированную заявку, новых не получает. Отмена уже начатой заявки отклоняется. GPS и фактические отметки исполнения пока отсутствуют.
8. Норматив длительности = технические работы + документы. Справочные минуты дороги не прибавляются повторно: дорогу даёт матрица маршрутов.

## Данные и ограничения

JSON: объект `{engineers: [...], requests: [...]}`. Примеры — `backend/samples` и `frontend/public/samples`. CSV инженеров и заявок можно загрузить одновременно. Поддерживаются UTF-8/UTF-8 BOM и Windows-1251.

Навыки: «Локальные работы», «Работы на подключение и дозаказы», «Аварийные работы». Старое «Подключение» нормализуется. Транспорт: car / walk / bike / transit. ID уникальны внутри каждого списка. Смены и окна — HH:MM в пределах одного дня; продолжительность — целые положительные минуты. Проверяются конечные координаты и их диапазоны. Лимит прототипа: 30 инженеров / 300 заявок, до 10 файлов по 10 МБ.

Таблицы Билайн: «Заявка», «Тип заявки HD», «Адрес», «Начало», «Окончание», «Бригада». Тип сопоставляется с существующим справочником нормативов; неизвестный тип пока использует локальный норматив. Для реальной работы проверьте это сопоставление, добавьте точные lat/lng и действительный список инженеров. Импорт показывает число пропущенных строк, приблизительных точек и явно предупреждает о сгенерированных сменах/навыках/транспорте.

**Известные приближения:**

- Общественный транспорт — расстояние по прямой × 1,3 и средняя скорость 18 км/ч, без расписаний и пересадок. На карте пунктир. Для настоящего transit нужен отдельный маршрутизатор с GTFS.
- Адрес без координат получает приблизительную точку из существующего локального справочника/эвристики, помечается estimated и предупреждением. Это не надёжное геокодирование.
- OSRM не учитывает живые пробки. За пределами московского графа расчёт может быть недоступен; скрытого переключения на прямые линии нет.
- `ROUTING_MODE=estimate` предназначен только для тестов/явно приблизительного локального расчёта; в compose он не включён.
- Сервис однопользовательский, без авторизации; опубликован только на 127.0.0.1. Для внешнего размещения нужны авторизация, TLS, резервные копии и ограничение доступа. Карта-подложка OSM требует интернета; атрибуция сохранена.

## Проверки

```powershell
docker compose exec backend python -m unittest discover -s tests -v
npm run build --prefix frontend
```

Тесты используют явный estimate-режим и не изменяют БД. Проверяются входной порядок baseline, окно начала, конец смены, приоритет срочных, навыки/транспорт, отмена, зафиксированный префикс, время события, валидация, устаревшая версия и большая смена.

Для разработки frontend: `cd frontend`, `npm ci`, `npm run dev`. Vite проксирует /api на localhost:8000; нужен отдельно доступный backend. Docker production не читает локальные frontend/.env-файлы. API документация описывает все структуры.

## Демонстрация на 5–7 минут

1. Демо 1 → «Построить план» → инженер → маршрут и объяснение заявки.
2. «Сравнение планов»: покрытия, инженеры, суммарный и индивидуальный пробег; при разном покрытии показано предупреждение.
3. Демо 2: неназначенные, фильтры и конкретные причины.
4. Демо 4: постройте план; добавьте срочную заявку с временем события; отмените будущую заявку или отметьте инженера недоступным. Зафиксированная часть сохраняется, все изменения перечислены и изменённые назначения подсвечены.
5. Демо 5: 12 инженеров / 72 заявки, сортировка заголовками, поиск, компактный список и кластеры.
6. Обновите страницу: набор и план восстанавливаются из PostgreSQL.
